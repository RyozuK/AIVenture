# AIVenture — Next-Generation Design Document

## 1. Vision

AIVenture is a **MUD-like text adventure game** where the entire world — rooms, items, creatures, quests, and lore — is procedurally generated by a language model in real time. The player navigates a persistent dungeon-crawl using natural language commands. Every room is new, every encounter is novel, and the world evolves based on the player's actions.

Unlike the original prototype, this design embraces **modern LLM capabilities** (structured tool calling, reliable JSON output, system prompts) and adopts a **clean MVC architecture** so the game engine can support console, web, or graphical clients without modification. The persistence layer is pluggable, enabling multiple independent save files and cloud sync.

---

## 2. Core Design Principles

| Principle | Rationale |
|---|---|
| **AI as the game master** | The LLM generates content and arbitrates outcomes, not a hand-authored script |
| **MVC separation** | The engine knows nothing about how content is displayed or how input arrives |
| **Pluggable LLM backend** | Any OpenAI-compatible endpoint works (OpenAI, Ollama, LM Studio, vLLM, etc.) |
| **Pluggable persistence** | Multiple save strategies (local JSON, SQLite, cloud) with zero engine changes |
| **Deterministic state** | Game state is a plain serializable object; the LLM never mutates state directly |
| **Tool calling over prompt hacking** | Structured function/tool calls replace fragile regex parsing of LLM output |
| **Memory management** | The LLM gets a curated context window, not an unbounded game log |

## 4. Model Layer

The Model is the single source of truth. It contains no I/O logic, no rendering, and no LLM calls. It is a set of plain data classes and the `World` graph that connects them.

### 4.1 Core Entities

#### `Position`
```
Position(x: int, y: int, z: int)
```
Immutable 3D coordinate. Hashable and comparable. Represents a point in the dungeon. Directions are relative offsets on this grid.

#### `Direction`
```
Direction: Enum { NORTH, SOUTH, EAST, WEST, UP, DOWN }
```
Includes `opposite()` and `offset()` methods. Centralized in one module — no duplication.

#### `Room`
```
Room(
    id: UUID,
    position: Position,
    name: str,
    description: str,
    exits: dict[Direction, Position],   # direction → neighbor position
    ambient_details: list[str],         # reusable flavor text
    connected_entities: list[UUID],     # entities currently in this room
    connected_items: list[UUID],        # items lying on the ground
    features: list[str],                # "pit", "altar", "locked door south"
    visited_count: int
)
```

#### `Entity` (Mobs, NPCs, Monsters)
```
Entity(
    id: UUID,
    name: str,
    description: str,
    entity_type: EntityType,   # MONSTER, NPC, PLAYER, BOSS
    room_id: UUID,
    hp: int,
    max_hp: int,
    attack: int,
    defense: int,
    inventory: Inventory,
    personality: str,          # LLM context for behavior
    is_hostile: bool,
    is_alive: bool,
    ai_behavior: str           # "patrol", "guard", "wander", "follow"
)
```

#### `Item`
```
Item(
    id: UUID,
    name: str,
    description: str,
    item_type: ItemType,
    stat_value: int,
    charges: int,              # -1 = unlimited
    is_equippable: bool,
    equip_slot: EquipSlot,     # HAND, HEAD, CHEST, LEGS, etc. or NONE
    is_key: bool,
    key_target: UUID | None,   # room or entity this key opens
    is_quest_item: bool,
    quest_id: UUID | None
)

ItemType: Enum { WEAPON, ARMOR, POTION, KEY, TREASURE, QUEST_ITEM, CONSUMABLE }
EquipSlot: Enum { HAND, OFF_HAND, HEAD, CHEST, LEGS, FEET, ACCESORY, NONE }
```

#### `Inventory`
```
Inventory(
    owned_items: dict[UUID, Item],       # items carried (not equipped)
    equipped: dict[EquipSlot, UUID],     # slot → item ID
    max_weight: int,
    current_weight: int
)
```
Methods: `add(item)`, `remove(item_id)`, `equip(item_id)`, `unequip(slot)`, `find(name_pattern)`, `to_dict()`.

#### `Quest`
```
Quest(
    id: UUID,
    title: str,
    description: str,
    giver_entity_id: UUID | None,
    status: QuestStatus,    # AVAILABLE, ACTIVE, COMPLETE, FAILED
    objectives: list[Objective],
    rewards: list[Reward]
)

Objective:
    type: "kill" | "collect" | "deliver" | "explore" | "talk"
    target: str | UUID
    required_count: int
    current_count: int
    is_complete: bool

Reward:
    type: "item" | "xp" | "gold"
    value: dict
```

#### `Player` (extends `Entity`)
```
Player(
    # inherited: id, name, description, hp, max_hp, inventory, ...
    gold: int,
    xp: int,
    level: int,
    active_quests: list[UUID],
    completed_quests: list[UUID],
    death_count: int
)
```

#### `World`
```
World(
    rooms: dict[Position, Room],
    entities: dict[UUID, Entity],
    items: dict[UUID, Item],
    quests: dict[UUID, Quest],
    player: Player,
    explored_positions: set[Position],    # rooms the player has seen
    generated_positions: set[Position],   # rooms the AI has created
    turn_count: int,
    world_seed: str,                      # descriptive theme for the LLM
    world_description: str,               # global lore context
)
```
Methods: `get_room(pos)`, `get_entity(uuid)`, `get_item(uuid)`, `move_player(direction)`, `add_room(room)`, `remove_entity(uuid)`, `to_dict()`.

### 4.2 State Serialization

The entire `World` object serializes to a single JSON-serializable dict. This dict is the canonical "save format." Persistence providers are responsible for storing and retrieving this blob.

## 5. LLM Service Layer

This layer encapsulates **all** interaction with the language model. The rest of the engine never imports an LLM library directly.

### 5.1 Design Philosophy: Tool Calling

Instead of prompting the LLM to produce JSON and parsing it with regex, we use **structured tool/function calling**. The LLM is given a set of defined tools and chooses which to invoke, with typed parameters. This is reliable across modern models (GPT-4, Claude, local models with function-calling support).

### 5.2 LLM Tools (Defined by the Engine, Called by the Model)

#### `generate_room`
```json
{
    "name": "generate_room",
    "description": "Generate a new room adjacent to an existing position.",
    "parameters": {
        "position": { "type": "object", "properties": { "x": "int", "y": "int", "z": "int" } },
        "name": { "type": "string" },
        "description": { "type": "string" },
        "exits": { "type": "array", "items": { "type": "string", "enum": [directions...] } },
        "items": { "type": "array", "items": { "$ref": "#/item_schema" } },
        "entities": { "type": "array", "items": { "$ref": "#/entity_schema" } },
        "features": { "type": "array", "items": { "type": "string" } }
    }
}
```

#### `describe_combat_outcome`
```json
{
    "name": "describe_combat_outcome",
    "description": "Determine the outcome of a combat exchange.",
    "parameters": {
        "attacker": { "type": "string" },
        "defender": { "type": "string" },
        "attacker_stats": { "type": "object" },
        "defender_stats": { "type": "object" },
        "narrative": { "type": "string" },
        "attacker_damage_dealt": { "type": "integer" },
        "defender_damage_dealt": { "type": "integer" },
        "attacker_alive": { "type": "boolean" },
        "defender_alive": { "type": "boolean" },
        "loot_dropped": { "type": "array", "items": { "$ref": "#/item_schema" } }
    }
}
```

#### `describe_item_use`
```json
{
    "name": "describe_item_use",
    "description": "Determine what happens when an item is used.",
    "parameters": {
        "narrative": { "type": "string" },
        "effects": { "type": "array", "items": { "type": "string" } },
        "charges_consumed": { "type": "integer" },
        "new_items": { "type": "array", "items": { "$ref": "#/item_schema" } }
    }
}
```

#### `generate_npc_dialogue`
```json
{
    "name": "generate_npc_dialogue",
    "description": "Generate a response from an NPC.",
    "parameters": {
        "npc_name": { "type": "string" },
        "dialogue": { "type": "string" },
        "mood": { "type": "string" },
        "quest_offered": { "type": "object", "nullable": true },
        "items_traded": { "type": "array", "nullable": true }
    }
}
```

#### `describe_action_outcome`
```json
{
    "name": "describe_action_outcome",
    "description": "Determine the outcome of a player action (searching, opening, etc.).",
    "parameters": {
        "success": { "type": "boolean" },
        "narrative": { "type": "string" },
        "discovered_items": { "type": "array", "items": { "$ref": "#/item_schema" } },
        "discovered_entities": { "type": "array", "items": { "$ref": "#/entity_schema" } },
        "new_exits": { "type": "array", "items": { "type": "string" } }
    }
}
```

### 5.3 Fallback: Non-Tool-Calling Models

If the chosen LLM backend does not support tool calling, the system falls back to **structured JSON prompts** with a strict schema and a validation/retry loop. The tool layer abstracts this away from the engine.

### 5.4 Context Management

The LLM does not receive the entire game state. Instead, the **context builder** in the Controller assembles a curated prompt containing:

1. **System prompt** — World theme, genre, tone, and rules.
2. **World lore** — High-level description of the setting (generated once at world creation).
3. **Current room** — Full details of the player's location.
4. **Visible entities** — Mobs and NPCs in the current room.
5. **Player summary** — Name, level, equipment, inventory (abbreviated).
6. **Recent history** — Last N turns of actions and outcomes (configurable window).
7. **Active quest context** — Objectives and status of current quests.
8. **The specific task** — "Generate a room to the north," "Resolve this attack," etc.

A **memory manager** compresses older history into summaries to keep context within token limits.

### 5.5 LLM Adapter Interface

```python
class LLMAdapter(ABC):
    """Interface for any LLM backend."""

    async def chat(
        self,
        system_prompt: str,
        user_messages: list[str],
        tools: list[ToolSchema] | None = None,
        response_format: str | None = None,  # "json_object"
    ) -> LLMResponse: ...

    async def generate_text(
        self,
        prompt: str,
        max_tokens: int = 256,
    ) -> str: ...


class LLMResponse:
    text: str                        # Raw text content
    tool_calls: list[ToolCall]       # Structured tool invocations (if any)
    finish_reason: str
    tokens_used: int


class ToolCall:
    name: str                        # Which tool was called
    arguments: dict                  # Parsed JSON arguments
```

Built-in adapters:
- `OpenAIAdapter` — Uses the `openai` SDK
- `OllamaAdapter` — Uses Ollama's `/api/chat` and `/api/generate` endpoints
- `CustomAdapter` — Any endpoint conforming to the OpenAI API spec (LM Studio, vLLM, litellm proxy, etc.)

Configuration is via a simple YAML/JSON config file:

```yaml
llm:
  provider: "ollama"                  # openai | ollama | custom
  endpoint: "http://localhost:11434"
  model: "llama3.1"
  api_key: "None"                         # optional, provider-dependent
  temperature: 0.9
  max_tokens: 1024
  supports_tool_calling: true

  # Fallback model for simple tasks (item names, short descriptions)
  light_model:
    provider: "ollama"
    model: "dolphin-mistral"
```

## 6. Controller Layer

The Controller is the brain. It receives inputs from any client, validates them against the Model, calls the LLM Service when needed, and returns results.

### 6.1 `GameSession`

```
GameSession(
    world: World,
    llm_service: LLMService,
    persistence: SaveManager,
    config: GameConfig
)
```

This is the top-level controller. One session per active game.

### 6.2 Command Processing Pipeline

```
Raw Input String
    │
    ▼
┌──────────────┐
│ Input Parser │  ── tokenizes "take the rusty sword" into:
│              │     { verb: "take", target: "the rusty sword" }
└──────┬───────┘
       │
       ▼
┌───────────────┐
│ Command Router │  ── maps verb → action handler
│                │     Handles synonyms: "take"/"get"/"grab", "go"/"move"/direction
└──────┬────────┘
       │
       ▼
┌────────────────┐
│ Action Handler │  ── Validates: can the player do this?
│                │     Resolves targets: which item/entity does "it" refer to?
│                │     Calls LLM if needed (combat, unknown actions)
│                │     Mutates the Model (state changes)
└──────┬─────────┘
       │
       ▼
┌──────────────────┐
│  Result Builder  │  ── Assembles the response:
│                  │     narrative text, state changes, items gained/lost
│                  │     New rooms generated, entities updated
└──────┬───────────┘
       │
       ▼
  Result Object
  {
      "narrative": "You swing your sword...",
      "state": { "player_hp": 7, "room": "...", "new_items": [...] },
      "turn": 42
  }
```

### 6.3 Natural Language Input

The command system accepts **natural language input**, not just verb+noun. The parser supports:

| Input | Interpretation |
|---|---|
| `north` | Move north |
| `go north` | Move north |
| `look` | Describe current room |
| `look at the goblin` | Describe the goblin entity |
| `take the sword` | Pick up the sword |
| `attack the goblin` | Initiate combat |
| `wear the armor` | Equip armor |
| `talk to the guard` | Initiate NPC dialogue |
| `search the room` | Search action (may reveal hidden items) |
| `use the potion` | Consume/use held item |
| `inventory` | Show inventory |
| `i found a secret passage` | Freeform input → LLM interprets |

For inputs that don't match a known verb, the LLM is consulted via `describe_action_outcome` to determine if the action is valid and what happens. This means the game accepts **any** natural language command.

### 6.4 Action-LLM Mapping

| Action Category | LLM Tool Used | Deterministic? |
|---|---|---|
| Movement to known room | None | Yes — room lookup |
| Movement to unknown room | `generate_room` | No — AI generates |
| Look / describe | None (model data) | Yes |
| Take / drop / equip | None | Yes — inventory logic |
| Combat attack | `describe_combat_outcome` | No — AI arbitrates |
| Use item (potion) | `describe_item_use` | No — AI decides effects |
| Talk to NPC | `generate_npc_dialogue` | No — AI roleplays |
| Search / explore | `describe_action_outcome` | No — AI discovers |
| Freeform command | `describe_action_outcome` | No — AI interprets |
| Death / resurrection | `describe_action_outcome` | No — AI narrates |

## 7. Persistence Layer

The persistence layer is fully isolated. The engine passes a `World` dict (or loads one). The persistence provider handles storage.

### 7.1 Interfaces

```python
class SaveProvider(ABC):
    """A single save strategy."""

    async def save(self, slot_name: str, world_state: dict) -> None: ...
    async def load(self, slot_name: str) -> dict | None: ...
    async def delete(self, slot_name: str) -> None: ...
    async def list_slots(self) -> list[str]: ...


class SaveManager:
    """Manages multiple save slots with a chosen provider."""

    def __init__(self, provider: SaveProvider): ...
    async def auto_save(self, session_id: str, world: World) -> None: ...
    async def load_slot(self, slot_name: str) -> World | None: ...
    async def create_slot(self, slot_name: str, world: World) -> None: ...
    async def list_slots(self) -> list[SaveSlotInfo]: ...
```

### 7.2 Built-in Providers

| Provider | Format | Use Case |
|---|---|---|
| `JsonFileProvider` | One JSON file per slot | Local single-player, simple |
| `SqliteProvider` | Single SQLite DB, multiple slots | Local with metadata (timestamps, thumbnails) |
| `CloudProvider` | REST API to remote storage | Multi-device sync |
| `MemoryProvider` | In-memory dict | Testing, temporary sessions |

### 7.3 Save Slot Schema

```python
SaveSlotInfo:
    name: str
    created_at: datetime
    modified_at: datetime
    player_name: str
    player_level: int
    turn_count: int
    current_room_name: str
    thumbnail: str       # One-line room description for menu preview
    metadata: dict       # Provider-specific extras
```

### 7.4 Auto-Save Strategy

- Auto-save every N turns (configurable, default: 10)
- Auto-save on every room generation (new content created)
- Manual save on explicit command
- Save slot name configurable per session

## 8. Client Layer

Clients communicate with the Controller through a **standard protocol**. A client sends a text command and receives a structured result.

### 8.1 Protocol

```python
# Client → Controller
CommandRequest(
    session_id: str,
    input_text: str
)

# Controller → Client
CommandResult(
    session_id: str,
    turn: int,
    narrative: str,              # Text to display to the player
    room_description: str,       # Current room (updated)
    player_state: dict,          # HP, inventory summary, etc.
    entities_visible: list[dict],
    items_visible: list[dict],
    new_quests: list[dict],
    game_over: bool,
    death: bool | None
)
```

### 8.2 Built-in Client: Console

A simple `telnet`/TCP or `stdin/stdout` client for local play. Renders `narrative` text to the terminal, shows a prompt, accepts input.

### 8.3 Extensibility

A web client could communicate via WebSocket using the same JSON protocol. A Discord bot client would send messages and parse reactions/commands. A graphical client could render room descriptions as scenes, show item sprites, etc. — all using the same Controller.

## 9. Game Flow

### 9.1 Session Start

1. Client connects
2. Player chooses: **New Game** or **Load Save**
3. **New Game**: LLM generates a world theme and starting room via `generate_room`. A starting quest may be offered.
4. **Load Save**: `SaveManager` restores the `World` state. Player resumes in their last room.

### 9.2 Main Loop (per turn)

```
1. Controller sends current room description to client (on first entry / after action)
2. Client receives input from player
3. Client sends CommandRequest to Controller
4. Controller parses input, resolves action
5. If action requires AI: Controller builds context, calls LLM via LLM Service
6. Controller applies LLM result to Model (mutates state)
7. Controller builds CommandResult with narrative and updated state
8. Controller triggers auto-save check
9. Controller sends CommandResult to client
10. Client renders result, returns to step 2
```

### 9.3 Death and Respawn

On player death:
- `GameSession` calls LLM with `describe_action_outcome` for a death narrative
- Player respawns at the last checkpoint (starting room or last save point)
- Death count increments
- Player retains quests and experience but may lose some gold/items (configurable)

### 9.4 World Generation Strategy

Rooms are generated **on demand** — only when the player moves into an unexplored direction. This keeps the world infinite while being lazy.

- The LLM receives the **position**, the **direction**, the **source room**, and the **world theme**
- Generated rooms are persisted immediately so revisits are consistent
- The LLM may generate items, entities, and hidden features in the room
- If a room generation fails or produces invalid output, the controller retries or falls back to a default room

### 9.5 Combat Flow

1. Player issues attack command against an entity
2. Controller assembles combat context (attacker stats, defender stats, equipment, environment)
3. LLM calls `describe_combat_outcome` with narrative and damage values
4. Controller applies damage, checks for death, processes loot
5. Controller sends combat narrative to client
6. If both alive, combat continues until one side yields or dies

Combat is **single-exchange per turn** by default, but can be configured for multi-round or automatic resolution.

## 10. Configuration

All external configuration is in a single `config.yaml` (or `config.json`):

```yaml
game:
  title: "AIVenture"
  max_context_turns: 15          # Turns of history to send to LLM
  auto_save_interval: 10         # Turns between auto-saves
  death_retains_xp: true
  death_item_loss: "random"      # none | random | all_consumables

llm:
  provider: "ollama"
  endpoint: "http://localhost:11434"
  model: "llama3.1:8b"
  temperature: 0.9
  max_tokens: 1024
  tool_calling: true

persistence:
  provider: "sqlite"
  path: "saves/aiventure.db"

client:
  type: "console"
  prompt: ":> "
  show_room_on_entry: true
```

## 14. Key Design Decisions and Rationale

### Why tool calling over prompt parsing?

The original implementation used regex to extract JSON from LLM output. This breaks constantly as models change. Tool calling gives the LLM a typed interface — it fills in structured parameters we define, and we get validated data back. For models without tool calling, a JSON-schema prompt with validation retry provides equivalent reliability.

### Why MVC?

A clean separation lets us:
- Write a web frontend without touching game logic
- Swap the LLM backend without changing persistence
- Test the Model in isolation without network calls
- Build a Discord bot that shares the same game engine as the console

### Why pluggable LLM endpoints?

The gaming community increasingly uses local models for privacy, cost, and customization. Supporting Ollama, LM Studio, and any OpenAI-compatible API means players can run the game entirely offline with a local 8B or 70B model.

### Why lazy room generation?

Generating the entire dungeon upfront wastes tokens and creates content the player may never see. On-demand generation means the world is effectively infinite, and the LLM always has the most relevant context (the room the player just left) to make coherent new content.

### Why isolate persistence?

Multiple save slots are essential for an exploratory game. Players should be able to branch their adventure, try different approaches, or keep a fresh save separate from their main run. A pluggable provider means we can add cloud sync later without architectural changes.

### Why async?

LLM calls are the bottleneck — they take seconds. The game must remain responsive during generation. `asyncio` allows the console to show a generation indicator, the web client to stream updates, and the Discord bot to send "generating..." messages, all without blocking.

## 15. Risk and Mitigation

| Risk | Impact | Mitigation |
|---|---|---|
| LLM generates inconsistent content | World feels disjointed | Strong system prompts with world theme; context includes recent rooms |
| LLM calls are slow | Poor responsiveness | Async I/O, streaming responses, loading indicators in clients |
| LLM costs add up (cloud APIs) | Expensive to run | Local model support, light model for simple tasks, token budgeting |
| Tool calling fails (malformed output) | Game stalls | Validation + retry loop; fallback to JSON-prompt mode |
| Context window overflow | LLM loses coherence | Summarization of old turns; sliding window; token budget per component |
| Player actions exploit LLM | Broken game state | Controller validates all state mutations; LLM suggestions are proposals, not commands |
